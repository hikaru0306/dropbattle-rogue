# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

ドロプシア (DROPSIA) — a Japanese-language puzzle-roguelike browser game (match same-color drops to battle enemies while choosing routes on a branching map). Published via GitHub Pages at https://hikaru0306.github.io/dropbattle-rogue/ — **pushing to `main` deploys immediately**. Also installable as a PWA (`manifest.json`).

There is **no build system, no npm, no bundler, no CI**. The entire game lives in `index.html` (~5,700 lines) as plain JavaScript with React 18 UMD loaded from local `lib/` files. There is no JSX — components use `h = React.createElement` calls. Open `index.html` directly in a browser (`file://` works) or serve with `python -m http.server` to run the game.

## Repository Layout

- `index.html` — the whole game: CSS, data tables, game logic, and React components in one file. Edit it directly; keep the single-file structure and do not introduce build tooling.
- `texts.js` — all user-facing strings (item names, descriptions, act names, tutorial text). Edit display text here, not in `index.html`.
- `cloud.js` — optional Firebase cloud save (anonymous auth → Google account linking; mirrors `localStorage` `db_*` keys to Firestore `users/{uid}`). Loaded dynamically only over http(s) and never with `?test=1` or `?nocloud=1`; the game works fully without it.
- `firestore.rules` — Firestore security rules; deployed manually by pasting into the Firebase console (not via CLI).
- `admin.html` — developer-only dashboard reading all users' progress (read access restricted to the admin UID in `firestore.rules`).
- `version.json` — displayed game version; bump it when shipping a user-facing feature (commit/PR titles include the tag, e.g. `(v0.0.5)`).
- `assets/` — final transparent PNGs (256px) and BGM. `assets_raw/` (gitignored) holds 768px generation output for reprocessing.
- `docs/敵行動パターン仕様書.html` — the design spec: enemy behavior patterns, scaling formulas, and art-style rules. Consult it before balance or art changes. `docs/ゲームデータ一覧.html` is auto-generated by `gen_docs.py` from live game data — regenerate it, don't hand-edit it.
- `lib/` — vendored React/ReactDOM production UMD builds (local so the game works offline / in app WebViews).

## Architecture of index.html

Data tables come first, then the single root component `DropBattle` (≈line 1492). Sections are marked with `// ===== 名前 =====` comment banners: 基本設定 (config), 裏ステージ (hard-mode "ura" stages), レリック (relics), キャラクター (characters), 敵定義 (enemy KINDS + behavior patterns), マップ生成 (branching map gen), エンカウント生成 (encounters), 袋 (drop lottery bag).

Key runtime concepts:
- `status` state machine: `title | map | battle | reward | clear | lose` — drives which screen renders.
- Two campaign modes: `omote` (3 acts) and `ura` (5 acts, unlocked per character).
- Most game state is duplicated into refs (`pRef`, `boardRef`, `enemiesRef`, …) so test hooks and async battle resolution read current values.
- Save data is `localStorage` keys prefixed `db_` (`db_cloud*` and `db_bak_*` are excluded from sync). A `Storage.prototype.setItem` hook in the `<head>` notifies `cloud.js` of dirty keys via `window.__dbDirty`.

URL parameters: `?test=1` (enables `window.__test` hooks, disables cloud and real-machine randomness), `&full=1` (keep test hooks but enable real mechanics — used by sim bots), `&fast=1` (speed up animations), `?nocloud=1`, `?fbemu=1` (Firebase emulator).

## Testing

No test framework. Testing is done with Playwright (Python, sync API) scripts at the repo root:

- `smoke_*.py` — headless smoke tests driving the game through `window.__test` (exposed only with `?test=1`). Run one directly: `python smoke_db.py`. They print progress steps, capture screenshots, fail on any console/page error, and end with `ALL SMOKE OK`.
- `sim_bot*.py` — autonomous playthrough bots (use `?test=1&full=1&fast=1`) for balance verification.
- `smoke_cloud_live.py` — real-Firebase sync test (serves the repo over localhost http).

**Important:** these scripts hardcode the author's Windows paths in `EXE`, `URL`, `SHOT`/`ROOT` constants at the top. Before running in another environment, replace them (use `p.chromium.launch()` with the locally available Chromium and a `file://` URL pointing at this repo's `index.html`; write screenshots to a scratch directory).

The `window.__test` API (defined in `index.html`, search for `テストフック`) includes `state()` (full game-state snapshot), `enter(nodeId)`, `commit(idx)`, `resolve()`, `weaken()`, `addAtk(v)`, `setPierce(v)`, `spawn(kinds)`, `jumpTo(row)`, `giveRelic(k)`, and shop/rest/forge helpers. Extend it there when a new feature needs test coverage, and keep `state()` cheap and side-effect-free.

## Asset Pipeline

Character/UI art is AI-generated and post-processed; the many root-level Python scripts are the pipeline:

- `gen_*.py` — generate art via a local ComfyUI API (`http://127.0.0.1:8188`) into `assets_raw/`. Most are one-off historical scripts; treat them as pattern references, not maintained APIs.
- `process_*.py` — `assets_raw/` → rembg (`isnet-anime` session) + corner-color keying → trim → 256px → `assets/`.
- `shot_*.py` — Playwright screenshot helpers for visual review.
- `patch_*.py` — historical one-off scripts that programmatically edited `index.html`; for new work just edit `index.html` directly.

Art style rules (enforced in prompts and by spec §7 of the docs): thick dark outlines, flat cel shading, chunky readable silhouettes — **no glow, neon, bloom, or glossy highlights**. Backgrounds must be transparent.

## Conventions

- Everything is in Japanese: UI text, code comments, commit messages, and docs. Write commit messages in Japanese following the existing log style (imperative summary, optionally with `(v0.0.x)` version tag).
- Comments in `index.html` frequently explain *why* (e.g. iOS Safari viewport quirks, animation pitfalls); preserve and match that style.
- The game must keep working from `file://` and offline — no CDN dependencies at runtime (React is vendored in `lib/` for this reason) and cloud features must degrade to no-ops.
- After gameplay changes, run at least one relevant smoke script (adjusting its paths as above) before considering the change verified.
